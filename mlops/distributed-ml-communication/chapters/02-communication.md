# 第二章:多卡要交換什麼——rank、集體通訊與網路成本

> [回導讀](../README.zh-TW.md) | [證據與來源](08-evidence.md)

> 上一章的結論是:突破記憶體牆與速度牆都要靠多卡,而多卡的共同代價是「跨卡交換資料」。這章回答:**多張卡一起算,彼此到底要交換哪些資料?有哪幾種基本的交換模式?一次交換要花多少時間?** 建立這套字彙與成本模型後,第三章才能逐一評斷每種切模型的方法「逼出多少通訊、在本平台跑得動嗎」。

## 先講字彙:rank 與 world size

當 N 張卡一起做一件事,我們給每張卡(嚴格說是每個參與的行程)一個編號,叫 **rank**(0, 1, 2, …, N−1);參與的總數叫 **world size**(這裡就是 N)。之所以要編號,是因為接下來的「集體通訊」都要指定「誰把資料送給誰、誰負責合併哪一段」,靠 rank 來定位。

多卡訓練最常見的模式是**同步**的:每一步所有 rank 各自算自己那份,然後在某個點上**一起**交換、對齊,再一起進下一步。這個「一起交換」的動作就是**集體通訊**(collective operation)——由所有 rank 共同參與、缺一不可的通訊。它是分散式訓練的心跳,也是本平台最可能的瓶頸。

## 四種基本的集體通訊(各配一個小例子)

用最小的例子說明四種模式。假設有 **4 張卡(rank 0–3)**,每張卡手上各有一小塊資料。

### AllReduce(全歸約):大家把數字加起來,每人都拿到總和

- **做什麼:** 每張卡有一個數值(或一個等長的陣列),把所有卡的對應數值**相加**(或取平均等),結果**每張卡都拿到同一份總和**。
- **小例子:** rank 0/1/2/3 手上各有梯度 `[1]`、`[2]`、`[3]`、`[4]`。AllReduce(求和)後,四張卡手上都變成 `[10]`。
- **用在哪:** 資料並行訓練每一步的核心——四張卡各用不同資料算出各自的梯度,AllReduce 求平均後大家拿到一致的平均梯度,才能同步更新旋鈕。
- **關鍵性質:** 它是**同步阻塞**的——要等**所有** rank 都把資料交出來才算得出總和,任何一張慢卡都會卡住全體(第四章的掉隊者問題就源於此)。

### AllGather(全收集):大家把各自的碎片拼成完整的一份,每人都拿到全貌

- **做什麼:** 每張卡有一塊**不同**的碎片,通訊後**每張卡都拿到拼起來的完整序列**。不做加總,只是收集。
- **小例子:** rank 0/1/2/3 各有 `[A]`、`[B]`、`[C]`、`[D]`。AllGather 後,四張卡手上都變成 `[A,B,C,D]`。
- **用在哪:** 當參數被切成碎片分存各卡(ZeRO-3/FSDP),要用某一層時得先把那一層的碎片 AllGather 拼回完整權重才能算(第三章)。

### ReduceScatter(歸約散布):大家把數字加起來,但每人只拿走總和的一段

- **做什麼:** 像 AllReduce 一樣相加,但結果**不是每人都拿全份**,而是**切開,每張卡只拿其中一段**。
- **小例子:** 四張卡各有長度 4 的陣列;ReduceScatter 後,rank 0 只拿到「所有卡第 0 段的和」、rank 1 拿第 1 段的和,以此類推。
- **關鍵關係:** **先做 ReduceScatter,再做 AllGather,等價於一次 AllReduce**——官方文件明言「Executing ReduceScatter, followed by AllGather, is equivalent to the AllReduce operation」[W5]。這個等式在第三章解釋 ZeRO/FSDP「把 DDP 的 AllReduce 拆成 ReduceScatter + AllGather」時是核心。

### AlltoAll(全交換):每個人手上都有給每個人的一份,徹底重新洗牌

- **做什麼:** 每張卡都準備了「分別要給每一張卡(含自己)的一小份」,通訊後每張卡收齊「來自每一張卡、原本指定給我的那些份」。相當於把資料沿另一個維度重新分片。
- **小例子:** rank 0 手上有 `[給0, 給1, 給2, 給3]`,其他卡同理。AlltoAll 後,rank 0 收到「各卡原本要給 0 的那份」= `[0給0, 1給0, 2給0, 3給0]`。
- **用在哪:** MoE(混合專家)把每個 token 送去它被指派的專家所在的卡,再把結果送回來——來回兩次 AlltoAll(第五章)。它是四種裡最「散」的通訊型態,對慢鏈路最敏感。

**四種一起看:** AllReduce 是「加總且人人有全份」、AllGather 是「拼碎片且人人有全貌」、ReduceScatter 是「加總但各拿一段」、AlltoAll 是「徹底重新洗牌」。它們搬過網路的資料量不同、對延遲/頻寬的敏感度也不同——要量化,需要一個成本模型。

## 一次通訊要多久:α + nβ 成本模型

先給白話:傳一則訊息的時間，可拆成兩部分——一段和訊息大小無關的**固定開銷**(不管傳 1 byte 還是 1 GB,每則訊息都要付出啟動、排隊、等第一個 byte 走完鏈路的延遲),加上一段**和大小成正比**的傳輸時間。用公式寫(這是分散式通訊的標準模型)[W2]:

要強調的是:這裡的固定開銷是「每則訊息的啟動延遲」,不是「每則訊息都要重新建立一條 TCP 連線」。實際上 NCCL(NVIDIA Collective Communications Library,NVIDIA 的 GPU 集體通訊庫;PyTorch、DeepSpeed 等框架底層實際搬資料、執行下面四種集體通訊的元件)在初始化時就建好長生命週期的連線並重複使用(第三章會再澄清),α 反映的是每則訊息本身的啟動與排隊成本,而非重新握手建連。

$$
T = \alpha + n\beta
$$

- **α(alpha):** 每則訊息的固定延遲(startup / latency),與大小無關。
- **β(beta):** 每個 byte 的傳輸時間(頻寬的倒數)。
- **n:** 傳輸的 byte 數。

這個簡單式子給出一條關鍵分界:**小訊息由 α 主導(延遲說了算),大訊息由 nβ 主導(頻寬說了算)**。論文原文即「minimizing latency for short messages and minimizing bandwidth use for long messages」[W2]。這解釋了為什麼同一種集體通訊,對 4 KB 的小訊息和 1 GB 的大訊息會用**不同的最佳演算法**,也解釋了為什麼「每層打一次網路的小訊息」(張量並行)和「整個模型偶爾傳一次大訊息」(管線並行)在本平台的命運截然不同。

### 把模型套到集體通訊

集體通訊由許多點對點訊息組成,成本隨演算法、卡數 p、訊息大小而變。舉兩個可核算的例子[W2]:

- **ring 版 AllGather:** $T = (p-1)\alpha + \tfrac{p-1}{p}\,n\beta$
- **Rabenseifner 版 AllReduce**(= ReduceScatter + AllGather):$T = 2\lg p\,\alpha + 2\tfrac{p-1}{p}\,n\beta + \tfrac{p-1}{p}\,n\gamma$

重點不在記住公式,而在兩個推論(信心:高):

1. 當 p 增大,AllReduce 的頻寬項趨近 $2n\beta$——**每張卡大約要送 2 倍 payload 過線,而且與被加總的數值內容無關,只和 byte 數與拓撲有關**。
2. ring 演算法「能吃滿頻寬」,但「延遲隨 GPU 數線性成長」,所以 NCCL 2.4 引入 double binary tree 以取得「full bandwidth and a logarithmic latency」[W3]。**本平台推論:** 只有 4 張卡,線性延遲還不是主要問題;主要問題是 β(每 byte 時間)在一般乙太網路上遠大於 NVLink,使大訊息 AllReduce 昂貴。

## 三個容易混淆的「頻寬」:algbw、busbw、NIC 線速

談通訊快慢時有三個數字常被混為一談,務必分開(這是後面判斷「通訊受不受限」的量尺):

- **algorithm bandwidth(algbw):** 最直觀的「資料量 ÷ 時間」,$\text{algbw} = S/t$[W1]。
- **bus bandwidth(busbw):** 用一個逐集體不同的修正因子換算而來,設計上用來反映硬體瓶頸的利用率:AllReduce 乘 $2(n-1)/n$;AllGather、ReduceScatter、AlltoAll 乘 $(n-1)/n$;Broadcast、Reduce 乘 1[W1]。官方明言 busbw「should reflect the speed of the hardware bottleneck : NVLink, PCI, QPI, or network」[W1]。
- **NIC(network interface card,實體網路介面卡)線速:** 該網卡本身的物理傳輸上限(例如 10/25/100 GbE)(本平台**未宣告**,repo 內查無任何線速數字——標為明確未知)。

**一句反面警語(信心:高):busbw 是一個換算慣例,不是 NIC 線速。** 更關鍵的是:當沒有 InfiniBand 或 RoCE(高速網路傳輸)時,NCCL 會退回用一般 IP socket 傳輸——「NCCL will fall back to using IP sockets」[W4]——而 TCP socket 傳輸通常只達 NIC 線速的一部分。所以本平台的實際 busbw 會**同時**低於 NIC 線速、又遠低於 NVLink 慣見的數百 GB/s。**這個「本平台實際 busbw」正是整份研究反覆指向、卻尚未量測的那個核心數字。**

## 怎麼把這個數字量出來:工具的職責與限制

- **iperf3:** 量主機層的 TCP/UDP/SCTP 吞吐,`-P` 開多流、`-R` 反向[W7]。**限制(推論):** 它只量主機網路吞吐,**不**量 GPU 之間的集體通訊頻寬;它給的是 NIC 線速的參考上界,不是 NCCL 實際能用到的頻寬。
- **nccl-tests:** 一組直接量集體通訊的工具(`all_reduce_perf`、`all_gather_perf`、`reduce_scatter_perf`、`all_to_all_perf`),直接報 algbw 與 busbw,是量「集體通訊實際表現」的正確工具[W6]。**注意:** 要量**跨主機**的多 rank 通訊,必須用 MPI(Message Passing Interface,一套在多台主機上同時啟動並協調多個行程的標準/啟動器)啟動、每台主機一個行程(細節見第七章的實驗設計);單機單行程量不到跨節點通訊。
- **獨立 RTT 量測:** 量 α(延遲項),與 iperf3 量的 β(頻寬項)互補。

有了字彙(rank、四種集體通訊)與量尺(α+nβ、algbw/busbw/NIC),就能回答上一章懸而未決的問題:**每一種「切模型的方法」到底逼出哪一種集體通訊、多少量、多頻繁?** 這正是第三章要逐一拆解的。
