# 第四章:一般網路與異質 GPU 的代價

> [回導讀](../README.zh-TW.md) | [證據與來源](08-evidence.md)

> 第三章把三種切法的機制與逼出的通訊講清楚,但每個判斷都帶著「在一般網路上」「無 NVLink 使…」的但書。這章兌現這些但書,回答:**把這些通訊放到本平台(每主機一張卡、無 NVLink、只有一般網路、四張卡型號還不一樣)上,代價到底變多大?平台的排程系統(K3s + Volcano + HAMi)能幫上什麼、幫不上什麼?**

## 先釐清平台前提:三件影響全局的事實

整份研究的推理都建立在對平台的幾個判斷上。這裡用白話講清楚每一個「是什麼、對決策的意義、證據有多硬」;詳細的檔案行號、被 git 忽略的庫存值、manifest/script 名稱都在〈證據附錄〉可查,正文不堆。

**事實一:型號不支援 NVLink 已由官方規格確認,現場配置仍是需求前提。** 1×5090 + 3×L40S、每主機一張卡、跨主機用一般乙太網路是需求設定,不是本次現場探測結果。RTX 5090 與 L40S 不支援 NVLink 則有官方規格直接支持[W40][W41];不能靠 repo 搜不到關鍵字來證明硬體能力。[第一章](01-problem-and-single-gpu.md)已解釋 NVLink 與為何不能替這些卡直接加裝。**對決策的意義:** 本題跨卡通訊以網路路徑估算;不能假設可加 NVLink 橋接器解決,也不能從缺少 NVLink 推定網卡線速或實際效能。

**事實二:此刻活著的叢集拓撲尚未驗證。** repo 裡看得到的節點名與 IP 只存在於一個被 git 忽略、屬某台操作者機器的本機檔;版本控制真正追蹤的只有一份佔位範例。所以那些節點名/IP **不能**當作「三台節點此刻是活的叢集成員、且以此拓撲跑 collective」的證據。**對決策的意義:** 第七章要量的網路路徑必須以現場唯讀讀出為準,不能照抄 repo 裡的示例拓撲。

**事實三:跨節點的網路後端是條件式選擇,不是既定事實。** 跨節點後端預設 `auto`:只有在 server↔agent 雙向直連成立時才選明文、較快的 host-gw,否則退回加密、MTU(maximum transmission unit,單一網路封包能攜帶的最大位元組數;越小則同樣資料要切成越多封包、每則訊息固定開銷占比越高)被夾小、頻寬特性不同的 wireguard-native;唯一以追蹤檔硬選 host-gw + 指定介面的,是一份**單節點**生產設定——而單節點根本沒有跨卡 collective。**對決策的意義:本平台實際跑哪一條後端、哪個介面、線速多少「尚未驗證」,是第七章要先量的未知數,絕不能預設 host-gw/eno2 為基線。**(三者的精確 path:line 見〈證據附錄〉。)

**由這三件事推出一個決定全局的結論(信心:高):** HAMi 把一張卡切成 3 份是**同一張實體卡的共享**(分時/分記憶體),對「多卡協同運算」毫無幫助;而四張卡分屬四台主機,彼此既無 NVLink、也無跨主機 PCIe P2P。所以本平台上「跨 GPU」永遠等於「跨主機一般網路」——第三章所有「TP 每層打網路」「ZeRO-3 逐層 AllGather」的但書,前提在此**全域**成立。

**還有一個界定信心邊界的結構事實:「一個 workload 一張卡」是現況,分散式訓練是「未來」形狀。** 生產 admission 硬性要求 GPU 數==1;架構文件把多 worker 訓練、Volcano PodGroup、gang scheduling 明列為未來能力。**意義:** 本研究討論的多節點並行,在本平台是「要不要走上、走上後值不值得」的前瞻決策,不是既有能力的調校;也因此**本平台沒有現成的分散式訓練實測可引用**,這正是各章信心邊界的來源。

**最後一個常被過度推論的點要先擋住:GPU 型號是排程維度,但不是「禁止混編」的禁令。** 節點以能力標籤區分型號、workload 用型號選擇器綁卡,契約要求逐型號驗證(通過 5090 不自動代表通過 L40S);**但契約並未禁止混編的 collective 群組**——範例 profile 就在同一個 workload 同時宣告兩種能力。所以後文「隔離出同質 3×L40S 群」的理由是**效能與驗證成本**,**不是**平台層的排程禁令。

## 一般網路上,通訊到底變多貴:對未知頻寬的敏感度分析

第三章算過:8B 用 ZeRO-3/FSDP 分片訓練,單步網路流量約是 DDP 梯度 AllReduce 的 1.5 倍[W10]。先估 DDP 梯度 AllReduce 的實際過線 byte 數:AllReduce 的過線量 ≈ $2(N-1)/N \times S$(第二章 busbw 因子),S = fp16 梯度 = 2Ψ = 16 GB,N=4:

$$
2 \times \tfrac{3}{4} \times 16\ \text{GB} = 24\ \text{GB／步(僅梯度歸約;FSDP 尚有前後向 AllGather,合計約 1.5×,數十 GB／步)}
$$

把這個 byte 數除以「本平台實測 busbw」(**目前未知**),就能看出對頻寬有多敏感:

| 假設 busbw B | 單步僅梯度歸約時間 | 判讀 |
|---|---|---|
| 1.25 GB/s(10 GbE、TCP 單流常見上界) | ≈ 19 秒 | 嚴重通訊受限 |
| 3 GB/s(25 GbE 一部分) | ≈ 8 秒 | 通訊受限 |
| 12.5 GB/s(100 GbE 線速理想) | ≈ 2 秒 | 視計算而定,可能平衡 |

對照計算側:8B 單 micro-batch 的前後向 FLOPs 約 6·Ψ·tokens(理論推估),在 L40S 級算力下對數千 token 落在數秒量級。**結論(信心:中,待第七章實測封閉):** 在 10–25 GbE 這類常見商用乙太網路上,8B 級全參數同步資料並行**很可能是通訊受限**;唯有 NIC 達 100 GbE 等級、且 NCCL 能吃到高比例線速時才可能平衡。**整個結論的翻轉開關,就是那個未知的 B**——這也是為什麼第七章把「量出 B」列為最高優先。

這張表也解釋了第三章反覆出現的「單卡放得下優先」:若一步要花 19 秒等網路、只花幾秒在算,那同樣的卡改成「各自跑單卡工作」反而總吞吐更高。

## 異質 GPU 為何毒害同步訓練

同步訓練每一步都以一次 AllReduce 作為 barrier(全體集合點):「all the processes have to wait for the stragglers before synchronizing gradients ... bottlenecks distributed performance to the slowest worker」[W32]。快卡先抵達 AllReduce,就卡在那等最慢的卡到齊——**整步時間 = 最慢卡的到達時間 + collective 時間**。

要區分四種「慢」(信心:高),因為對策完全不同:
- **計算不均:** 各卡每步計算量不同(異質算力,或資料有 outlier[W32])。
- **網路慢:** 某條鏈路慢或不穩(「unstable network I/O」[W32])。
- **背景共享:** 同卡/同機被其他行程佔用——本平台 HAMi 的 `shared` 模式**核心 % 只是排程配額,不是硬隔離或延遲保證**(`docs/workload-contract.md`),共享時鄰居會製造抖動。
- **真正 deadlock:** collective 對不齊(rank 數/順序/大小不符),本質不同,不會自行恢復。

還有持久 vs 暫態之分:異質硬體造成的是**持久掉隊者**——「persistent stragglers, which can be caused by hardware degradation or a network issue ... leading to nearly no straggler mitigation」[W32],一般的緩解手段對它幾乎無效。

**兩個獨立效應在異質群裡疊加:**
1. **記憶體上界被最小卡綁住:** 等量分片下每卡 16Ψ/N,32 GB 的 5090 是天花板(第三章)。要嘛降批次/模型遷就 5090,要嘛給 5090 較小分片(非預設,需自訂)。
2. **到達時間被最慢卡綁住:** 即使塞得下,異質算力使各卡到達 AllReduce 的時間不同 → barrier 等最慢者[W32]。而且異質 VRAM 會逼出不同的 per-rank micro-batch → 進一步放大到達差(此為作者推論,非 [W32] 直接引文:不同 VRAM → 不同 batch → 不同計算時間 → 同一 barrier 上到達不齊)。

**一句必須守住的話(反面證據,信心:高):不可預設 RTX 5090 在所有工作負載都快於 L40S。** 兩者架構不同(Blackwell 消費級 vs Ada 資料中心級),對不同 kernel、記憶體頻寬、精度路徑各有優劣;5090 只有 32 GB,在需要大 activation/大 batch 的工作上反而更早受限。真正的快慢要逐工作負載實測,不能由型號名推定(第七章 Phase 4)。

## 從平台原始碼看排程隔離:一條端到端追蹤

要判斷「平台能不能把分散式訓練正確地擺起來」,得追一條「工作宣告 → Volcano 排程 → HAMi 配額」的路徑,並誠實區分**已實作的邊**與**尚屬文件契約的邊**。

**先走一個具體例子(把抽象路徑落地):** 假設要在 3×L40S 上起一個三 worker 的同步訓練。理想路徑是——每個 worker 發布一份機器可讀的宣告(要幾張卡、最小 VRAM、要哪個 GPU 型號能力);提交成一個 Volcano Job,把「三個 worker 必須一起入場」寫成 gang 語意(`minAvailable=3`);Volcano 的 gang plugin 保證三者要嘛一起排上、要嘛都不排(避免兩個先卡在那裡空等第三個);型號選擇器把它們落到三台 L40S;HAMi 在每台上把**整卡**(exclusive)配給該 pod;三個 pod 起來後靠 NCCL 跨選定的網路後端互通。

**但這條路徑目前只走得到一半,關鍵一段是「整合縫」而非既有的邊:** 上述「機器可讀宣告」用的 CRD(Kubernetes Custom Resource Definition,自訂資源定義——把一種新的、叢集原生可提交的物件型別註冊進 Kubernetes,讓使用者能像宣告內建資源一樣宣告它)**尚未實作**——文件明言「This CRD does not exist yet」,repo 內沒有接收、驗證或把它轉譯成 Job 的程式碼。真正 checked-in 可跑的,只是一個**單副本**的 Volcano smoke Job(`minAvailable:1`)。所以例子裡從「宣告」到「三 worker gang Job」這一步,現況是設計意圖、不是既有能力。

**這條追蹤揭示兩個尚無證據的行為(gap):**
- **min-member>1 的真實 gang 未曾出現:** 全 repo 的 Volcano Job 都是 `minAvailable:1`,多 worker gang 只在架構文件以「Future」出現。所以「分散式訓練會被平台正確 gang 起來」是**設計意圖已具備、實作尚待驗證**。
- **HAMi 分片對分散式運算無益:** 一張卡的 3 個 vGPU 分片是同一實體卡的共享,不是可跨卡協同的運算單元;分散式訓練需要的是 N 個 pod 各拿**整卡**分佈在 N 台主機,再靠 NCCL 通訊。

**排程能做到與做不到的(白話結論):**
- **能力:** 以節點標籤選 GPU 型號;L40S 生產路徑用 taint/toleration + 主機名綁定 + namespace 配額,鎖成恰好一份配額。
- **限制:** HAMi 的核心 % 是排程配額、**不是**硬隔離或延遲保證;容量收據是 15–300 秒的 best-effort、不保證免於同步 OOM。共享配額**無法**保證掉隊者不因鄰居抖動而出現。

(以上每一步的 manifest / plugin / 契約條款精確 path:line——WorkloadProfile 欄位、gang 與 deviceshare/binpack plugin 清單、HAMi 的 deviceSplitCount/gpuMemoryFactor 與容量換算、admission 單卡硬鎖——均見〈證據附錄〉本地錨點。)

## 架構評估:「5090 獨立跑低延遲小批次推論 + 3×L40S 同質群」

把上面的機制收斂成一個架構判斷。**建議:採納。理由(信心:高):**
1. **同質群消除異質掉隊者與最小卡瓶頸:** 3×L40S 同型號、同 46 GB、同算力,同步 collective 的到達差只剩資料/網路抖動,不含型號差;分片天花板統一為 46 GB。直接對應 [W32] 的持久掉隊者與第三章的最小卡上界。
2. **5090 獨立跑低延遲小批次推論,發揮強項又不拖累群體:** 小批次推論不需 collective barrier,把 5090 從任何同步群拉出來,它就不會成為 barrier 的最慢/最小者。
3. **驗證成本與平台粒度一致:** 逐型號驗證下,混編群組要為兩個型號各付一次 qualification。這是**成本與效能**理由,不是平台排程禁令。

**必須精確界定排除範圍(修正過度推論):** 上述理由(最小卡天花板 + 到達差)是**等量分片同步訓練(DDP/ZeRO/FSDP)**的特定症狀,不是「5090 不得參與任何跨卡協同」的物理通則。**管線並行天生支援非對稱切分**:可把較少層分給 32 GB 的 5090、較多層分給 46 GB 的 L40S。若徹底排除 5090,四卡總 VRAM 會由 170 GB(3×46+32)降到 138 GB,反而扼殺某些大模型的可行性。**正確結論:嚴禁把 5090 混入等量分片同步訓練;但保留它作為「非對稱 PP 推論節點」的合法位置。**

**反例與代價(誠實列出):**
- 若某模型**恰好**只能靠四張卡湊出足夠 VRAM,排除 5090 就少一張卡,可能被迫放棄該模型或改用 offload——此時「非對稱 PP 用滿 4 卡」才是保留 5090 的方式。
- 3×L40S 是奇數,某些偏好 2 的次方的 TP/PP degree 不整除,需以 PP/DP 為主。
- 5090 閒置時算力未被群體利用(機會成本);可用 Volcano queue 讓它接互動/背景工作填補。

**示意設定(不部署,僅示意):** 同質訓練群以 `nodeSelector:{gpu.compute-capability:"89"}` + exclusive + Volcano gang(minAvailable:3)綁三台 L40S;5090 以 `nodeSelector:{gpu.compute-capability:"120"}` 跑獨立 Deployment+Service 的低延遲推論。未來 trace 應把每步分解為 compute / 到達差 / 傳輸 / 重疊 四段(第七章 Phase 4)以驗證掉隊者效應。

**至此,資料並行、模型並行在本平台的代價都已量化。** 還剩一種模型——混合專家(MoE)——它引入了前三章沒出現過的**第三種通訊型態**(AlltoAll),而且在本平台特別棘手。下一章專門處理它。
