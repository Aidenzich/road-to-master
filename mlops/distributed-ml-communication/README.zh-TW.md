# 分散式 AI/ML 運算與通訊瓶頸:技術研究導讀

> **繁體中文完整筆記** | [English overview](README.md) | [MLOps 索引](../README.zh-TW.md)

> 本文為 2026-09-08 技術 Spike 的完整導讀與章節整理,不是已完成的硬體效能報告。公開版僅將本機路徑改為專案相對描述、移除私人節點識別資訊;未執行 GPU 實驗。

這份研究要回答一個很具體的工程問題:**手上有四張分散在不同主機、彼此沒有高速專用連線、只能走一般網路線互通的 GPU,想拿它們訓練或服務大型 AI 模型,該怎麼擺放模型、哪些做法划算、哪些是自找麻煩?**

本研究只做技術分析與未來實驗設計,**不**實際跑 GPU 壓測、不部署模型、不動任何叢集。研究模式是「本地平台約束 × 外部框架與論文一手來源」的對照(`local-plus-web`);撰寫與查閱日期 2026-09-08。

---

## 一句話結論(白話,細節與信心邊界見各章)

在這套「每台主機一張卡、卡與卡之間沒有高速專用互連、跨卡一律走一般網路」的硬體上:

- **能用單卡,先建立單卡基線。** 模型放得下一張卡時,單卡部署通常較簡單且免跨卡通訊,但不保證所有負載下都最快;放不下,可先評估壓縮權重是否符合品質要求。
- **真的要多卡,優先評估「交換資料少」的擺法。** 沿著模型的層把它切成幾段、只在段與段的交界傳中間結果(管線式切法),有機會減少「每一層都要所有卡互相對答案」(逐層切法)的頻繁同步成本。但前者也會空轉、負載不均,勝負仍須量測;不能從「無 NVLink」直接推出後者必敗。
- **別把快慢、大小不一的卡混進同一個「同步訓練」隊伍。** 這種隊伍每一步都要等最慢、記憶體最小的那張卡,混編等於自願被拖住。

**這些結論的信心邊界:** 背後的機制與可核算的成本(誰要送多少資料、誰要等誰)都有一手論文與官方文件支撐,信心高;但**本平台實際能跑多快,取決於一個目前尚未量測的數字**——跨主機網路實際的集體通訊頻寬。所有「會不會被通訊拖垮」的判斷都掛在這個數字上。

**下一步該做的事:** 先量出這個數字(見〈第七章:未來實驗設計〉的第一項),因為其餘所有結論都建立在它之上。

## 建議閱讀順序

本導讀是穩定入口;完整內容拆成七章,依下列順序閱讀最順,但每一章也可獨立定位。每章開頭會接住上一章留下的問題、結尾說明為何需要下一章。

1. **[問題設定與單卡的極限](chapters/01-problem-and-single-gpu.md)** — 一次訓練或推論,一張 GPU 的記憶體到底裝了什麼?為什麼常常放不下、或放得下也不夠快?(這章先教 NVLink、PCIe、乙太網路的差別與現有 GPU 為何不能加裝 NVLink,再教參數、梯度、優化器狀態、activation、精度。)
2. **[多卡要交換什麼:rank、集體通訊與網路成本](chapters/02-communication.md)** — 多張卡要一起算,彼此必須交換哪些資料?四種基本的「集體通訊」各做什麼?一次通訊要花多少時間?(這章教:rank、world size、AllReduce/AllGather/ReduceScatter/AlltoAll、通訊成本模型。)
3. **[三種切模型的方法:資料並行、張量並行、管線並行](chapters/03-parallel-strategies.md)** — 資料並行、張量並行、管線並行三種做法分別怎麼改變「資料放在哪張卡」與「要交換什麼」?各自何時受通訊限、何時受計算或空轉限?(這章教:資料並行的三種分片程度、逐層切矩陣、沿層切段,以及各自逼出的通訊。)
4. **[一般網路與異質 GPU 的代價](chapters/04-ethernet-and-heterogeneous.md)** — 把上述做法放到「沒有高速互連、只有一般網路、四張卡型號還不一樣」的真實平台上,代價變成什麼?平台的排程系統能怎麼隔離、又有哪些做不到?
5. **[混合專家模型與它獨有的通訊](chapters/05-moe.md)** — 混合專家模型的 token 路由如何引入「第三種」通訊型態,以及為什麼它在本平台特別棘手。
6. **[平台取捨、策略適配矩陣與建議](chapters/06-platform-decision.md)** — 把前五章綜合成一張「候選做法 × 本地約束」的對照表、最強的反面證據及其處置、明確建議,以及什麼情況會翻轉建議。
7. **[未來實驗設計(五面向)](chapters/07-experiments.md)** — 要把上述判斷從「理論推估」變成「實測確認」,該設計哪些實驗:假設、環境、變因、範例命令、指標、每個結果會改變哪個決策。本次只設計、不執行。

另有 **[證據附錄](chapters/08-evidence.md)**,收錄所有本地程式碼的精確位置(檔案:行號)、外部來源的網址與逐字引文、以及明確標注的證據缺口。正文只留必要引用與其含義,詳細行號與長引用都在附錄可追溯。

## 範圍與非目標

- **研究問題:** 在 1×RTX 5090 + 3×L40S、無 NVLink(GPU 間高速專用互連)、跨主機靠 PCIe 與標準乙太網路、以 K3s + Volcano + HAMi(容器編排與 GPU 排程堆疊)為平台的背景下,三大類把模型分到多卡的做法——資料並行、張量並行、管線並行——與混合專家模型的專家並行,其底層機制、效能取捨與適用條件為何?各種跨卡「集體通訊」的瓶頸在哪?(這些做法各自的英文簡稱與符號,皆於對應章節第一次被用到之前以白話從頭教懂;此處只用中文完整名稱陳述研究題目。)
- **具名本地目標:** `gpu-cluster-iac`(git HEAD `ae6bba2`,唯讀檢視)。
- **由需求給定的硬體配置,與已核對的型號限制:** 1×RTX 5090(32 GB)、3×L40S(每張約 46 GB 可用),依題意分屬不同主機,主機內經 PCIe、主機間經標準乙太網路。兩種 GPU 的官方規格皆明列不支援 NVLink[W40][W41],不是僅假定「尚未購買橋接器」;概念與升級邊界見第一章。現場拓撲、NIC 線速、實際路由、GPU 配額、背景負載**仍為未知**,凡依賴這些者一律做明示假設的敏感度分析,不冒稱現場事實。
- **非目標(本次明確不做):** 不跑 GPU benchmark、不部署/訓練/推論壓測、不操作遠端叢集、不安裝套件、不執行下載程式碼、不改產品或叢集設定、不取模型權重。凡涉及「本機實際數字」者一律標為未知並給封閉配方。
