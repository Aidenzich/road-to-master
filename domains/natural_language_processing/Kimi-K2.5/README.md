## Introduction

Kimi K2.5 sets out to solve two concrete problems. First, how to train a language model to be good at both text and vision **under a fixed vision-text token budget** without the two dragging each other down. Second, how to free agentic models from "one-step-after-another" sequential tool calling, because even a model that can reason over hundreds of steps (like Kimi K2-Thinking) still sees its inference time grow linearly with the number of steps, so complex tasks become unusably slow. Both problems are real: multimodal models have long faced the "add vision, text regresses" trade-off, and the latency of long-horizon agents is a hard bottleneck for productization.

The report's high-level solutions map onto these two points. For the first, K2.5 builds on Kimi K2 — a 1.04-trillion-parameter MoE language model — and does **joint pretraining** on ~15 trillion mixed vision-text tokens, arguing that "early, low-ratio" vision fusion beats the conventional "late, high-ratio" injection; post-training then uses zero-vision SFT (bootstrapping visual tool use from text-only SFT) plus joint text-vision RL. For the second, K2.5 proposes **Agent Swarm**: a trainable orchestrator that dynamically decomposes a task, spawns frozen subagents to execute in parallel, and learns "whether, when, and how" to parallelize via Parallel-Agent Reinforcement Learning (PARL).

How is success measured? The report compares against three proprietary models — Claude Opus 4.5, GPT-5.2, Gemini 3 Pro — and two open-source models — DeepSeek-V3.2, Qwen3-VL — on a large benchmark suite spanning reasoning, code, multimodal (image and video), agentic search, and computer-use; the core metrics include accuracy or success rate on HLE, AIME 2025, SWE-Bench Verified, BrowseComp, OSWorld-Verified, etc., plus the speedup factor by which Agent Swarm shortens the wall-clock time needed for WideSearch to reach a target Item-F1. One caveat: K2.5's own scores mostly use public benchmarks but re-run them under the authors' own sampling settings (default temperature 1.0, top-p 0.95, context 256k), and a few items (the SWE-Bench series) use an "internally developed evaluation framework"; meanwhile many baselines in Table 4 are starred, meaning they are the authors' "internal re-tests" rather than officially published values.

## First Principles

### Model family and architecture: K2.5 = K2's MoE language backbone + MoonViT-3D vision encoder

Kimi K2.5 is not a new model trained from scratch, but an extension of Kimi K2 into native multimodality. The language backbone reuses Kimi K2: a 1.04-trillion-total-parameter MoE transformer activating 32B per token, with 384 experts and 8 selected per token (sparsity 48), trained with the MuonClip optimizer paired with QK-Clip for stability. The multimodal architecture has three parts: the native-resolution vision encoder MoonViT-3D, an MLP projector, and the aforementioned K2 MoE language model — a design inherited from Kimi-VL.

The repository model card adds details not listed in the paper body: the model uses MLA attention, SwiGLU activation, 61 layers (of which 1 is dense), attention hidden 7168, MoE hidden 2048 per expert, 64 attention heads, 1 shared expert, vocabulary 160K, context length 256K, and a MoonViT vision encoder of ~400M parameters. Only one "post-trained" checkpoint is actually released — there is no base version or multiple sizes — so the "model family" is really just a single ~1T MoE.

The key to MoonViT-3D is that "images and video share the same set of parameters and embedding space." It is initialized from SigLIP-SO-400M and adopts NaViT's patch packing to process images at native resolution; for video, up to four consecutive frames are treated as one spatiotemporal volume, with 2D patches flattened and packed together so the same attention operates across both space and time. Before entering the MLP projector, lightweight temporal pooling aggregates each temporal chunk, yielding 4× temporal compression that extends the processable video length fourfold without needing an extra video-specific module.

### Early, low-ratio vision fusion: a core claim resting on a single ablation table

The report's most counterintuitive claim is that, under a fixed total vision-text token budget, **early injection at a low vision ratio** beats the conventional late-high-ratio approach. Table 1 is the main evidence for this claim — three strategies compared under the same token budget across six capabilities:

| Vision Injection Timing | Vision Ratio | Vision Knowledge | Vision Reasoning | OCR | Text Knowledge | Text Reasoning | Code |
|-|-|-|-|-|-|-|-|
| Early (0%) | 10%:90% | 25.8 | 43.8 | 65.7 | 45.5 | 58.5 | 24.8 |
| Mid (50%) | 20%:80% | 25.0 | 40.7 | 64.1 | 43.9 | 58.6 | 24.0 |
| Late (80%) | 50%:50% | 24.2 | 39.0 | 61.5 | 43.1 | 57.8 | 24.0 |

Early is highest in five of the six columns (Text Reasoning slightly loses to Mid's 58.6). The appendix Figure 9 renders the same ablation as full training curves: the learning curves of the three ratios (10:90, 20:80, 50:50) across the six capabilities, where 10:90 (early low-ratio) converges to the highest final score on almost every item, while the two curves that inject vision later (20:80 / 50:50) first drop then recover on text benchmarks (Text Knowledge, Text Reasoning, Coding) as soon as vision data comes in — this is what the authors call "dip-and-recover," attributed to modality domain shift disrupting the existing language representations.

The actual recipe used is in Table 3's three stages: ViT training (1T tokens, seq 4096) → joint pretraining (15T, seq 4096) → long-context mid-training (500B→200B, seq 32768→262144, extrapolated with YaRN).

Note the limits of how persuasive this table and set of curves are: it presents only three discrete ratios and a single token budget, and the column-score gaps are tiny (e.g., Vision Knowledge 25.8 vs 24.2 differs by only 1.6), with no variance or confidence intervals across multiple runs — a "5-to-1 win" at this scale may just be noise. Figure 9's curves do make "10:90 converges highest" more visually explicit, but the gaps at the tail of the curves likewise carry no annotated variance bands.

### Training infrastructure: DEP lets multimodal training reuse the text-only parallelism strategy

The biggest engineering pain of stuffing a vision encoder into an existing large language model training pipeline lies in Pipeline Parallelism (PP): the traditional approach places the vision encoder and text embedding together in the first pipeline segment (Stage-0), but image count and resolution vary widely, so Stage-0's compute and memory usage fluctuate wildly, forcing engineers to customize the PP configuration for the VLM (e.g., manually adjusting the number of decoder layers in Stage-0 to reserve memory) and preventing direct reuse of the highly optimized parallelism strategy from text-only training. K2.5 (§4.5) proposes the **Decoupled Encoder Process (DEP)**, which exploits the vision encoder's special position in the computation graph (it is the very start of the forward pass and the very end of the backward pass) to split each training step into three segments: (1) Balanced Vision Forward — first run a forward pass over all vision data of the entire global batch; because the vision encoder is small, it is replicated onto all GPUs, with the load evenly distributed across cards by image/patch count, discarding intermediate activations and keeping only the final output, then routing the results back to PP Stage-0; (2) Backbone Training — the forward and backward passes of the main transformer backbone; because the previous segment discarded the vision intermediate activations, it can now fully reuse the parallelism strategy validated on text-only training; (3) Vision Recomputation & Backward — recompute the vision encoder forward pass and then do the backward pass to obtain gradients. This both resolves PP's load imbalance and decouples the vision encoder's optimization strategy from the main backbone; the report states it therefore "seamlessly inherits" K2's parallelism strategy, achieving **90% of the multimodal training efficiency** relative to text-only training.

Training scale and hardware: K2.5 is trained on an NVIDIA H800 cluster (8×400 Gbps RoCE inter-node), using 16-way PP (with virtual stages) + 16-way EP + ZeRO-1 data parallelism, trainable on any number of nodes that is a multiple of 32, with EP's all-to-all communication overlapped with computation via interleaved 1F1B scheduling; to save memory it additionally does selective recomputation, compresses insensitive activations to FP8-E4M3, and offloads the remaining activations to CPU. These are clear engineering contributions, but they are also the non-reproducible part — the repository only provides inference deployment (vLLM/SGLang), and DEP and this parallelism strategy come with no training code, hyperparameters, or data-composition details, so readers can take the design ideas but cannot re-run them.

### zero-vision SFT and cross-modal transfer: visual RL actually makes text stronger

K2.5's post-training makes a bold choice: **use only text-only SFT** to bootstrap visual and agentic capabilities (zero-vision SFT). The method proxies all image operations as programmatic operations in IPython (e.g., estimating object size or counting via binarization), treating it as a generalization of conventional visual tool use. The authors say that adding manually designed visual trajectories actually hurts generalization, conjecturing this is because joint pretraining already established sufficiently strong vision-text alignment.

Next comes outcome-based visual RL, targeting three classes of "must look at the image to answer correctly" tasks: visual grounding and counting, chart and document understanding, and STEM requiring visual input. The report's strongest cross-modal argument is Table 2: doing visual RL alone actually improves text-only benchmarks — MMLU-Pro 84.7→86.4, GPQA-Diamond 84.3→86.4, LongBench v2 56.7→58.9. The authors interpret this as visual RL improving calibration in "structured information extraction" scenarios. This is a clean, checkable causal claim, but with only three benchmarks each gaining 1.7–2.2 percentage points, the sample is still thin.

### Joint RL's loss, reward, and Toggle: writing "save tokens" into the objective

For each question $x$, K2.5's RL samples $K$ responses with the old policy $\pi_{old}$ and optimizes the following (Eq. 1, notation per the report):

$$L_{RL}(\theta) = \mathbb{E}_{x \sim D}\left[ \frac{1}{N} \sum_{j=1}^{K} \sum_{i=1}^{|y_j|} \mathrm{Clip}\!\left(\frac{\pi_\theta(y_j^i \mid x, y_j^{0:i})}{\pi_{old}(y_j^i \mid x, y_j^{0:i})}, \alpha, \beta\right)\big(r(x,y_j) - \bar{r}(x)\big) - \tau \left(\log \frac{\pi_\theta(y_j^i \mid x, y_j^{0:i})}{\pi_{old}(y_j^i \mid x, y_j^{0:i})}\right)^{2} \right]$$

The probability ratio in the formula is a **per-token conditional probability ratio**: $y_j^{0:i}$ is the prefix before the $i$-th token of the $j$-th response, $\pi_\theta(y_j^i \mid x, y_j^{0:i})$ is the probability of generating the $i$-th token conditioned on that prefix, $N = \sum_{i=1}^{K} |y_i|$ is the total number of generated tokens over the whole batch, and $\bar{r}(x)$ is the average reward of the $K$ responses to the same question (serving as the baseline). The sum contains two terms: the first is the clipped probability ratio times the advantage, where crucially this token-level clipping **only checks whether the log-ratio falls within the interval $[\alpha,\beta]$**, independent of the sign of the advantage, and tokens falling outside the interval have their gradient zeroed directly; the second term $-\tau\big(\log \tfrac{\pi_\theta}{\pi_{old}}\big)^{2}$ is a per-token **log-ratio squared penalty** ($\tau>0$) that additionally pulls the new and old policies closer. Together they explicitly limit the off-policy drift caused by training/inference framework inconsistency, which is the main difference from standard PPO clipping.

On the reward side, verifiable tasks use a rule-based outcome reward plus an additional budget-control reward to improve token efficiency; open-ended tasks use Generative Reward Models (GRM). To balance "saving tokens" against "test-time expansion," the report proposes **Toggle**: alternating two phases every $m$ iterations — Phase0 constrains within a per-question estimated token budget (and only applies it when that question's average accuracy exceeds a threshold $\lambda$), and Phase1 relaxes to the maximum token count to encourage test-time expansion. The question-dependent budget is taken from the "$\rho$-th percentile of correct-response lengths" (Eq. 2):

$$\mathrm{budget}(x) = \mathrm{Percentile}\big(\{\,|y_j| \mid r(x,y_i)=1\,\},\ \rho\big)$$

The report states that Toggle reduces the average output on K2 Thinking by 25–30% with almost unchanged performance, and claims that training only on math/code also generalizes to token reduction on GPQA and MMLU-Pro. Figure 5 concretizes this "save tokens but keep the score" dual objective with two radar charts: the left is per-benchmark accuracy (grey before Toggle, blue after), annotated Improved: 5 / Degraded: 2, where the two that regress (e.g., one −2.4%, another −1.0%) are both small in magnitude; the right is token usage (grey before Toggle, orange after), annotated Reduced: 7 / Increased: 0, with the orange polygon visibly shrinking inward, meaning token usage dropped on all seven benchmarks.

The left chart is accuracy (grey before Toggle, blue after), annotated Improved: 5 / Degraded: 2, with regressions all within a few percentage points; the right chart is token usage (grey before Toggle, orange after), annotated Reduced: 7 / Increased: 0, with the orange polygon shrinking overall, indicating tokens dropped across the board.](imgs/fig5_toggle.png)

### Agent Swarm and PARL: parallel orchestration that writes latency into the reward

The core of Agent Swarm is a decoupled architecture: **a trainable orchestrator + frozen subagents** (instantiated from a fixed intermediate policy checkpoint). Deliberately not doing end-to-end joint optimization is meant to sidestep two difficulties — ambiguous credit assignment and training instability; by treating subagent outputs as environment observations rather than differentiable decision points, "high-level coordination" and "low-level execution" can be decoupled. PARL's reward is the sum of three terms:

$$r_{PARL}(x,y) = \lambda_1 \cdot r_{parallel} + \lambda_2 \cdot r_{finish} + r_{perf}(x,y)$$

$r_{perf}$ evaluates the quality of the final solution; $r_{parallel}$ encourages spawning subagents to avoid "serial collapse" (degenerating into the local optimum of a single agent); $r_{finish}$ requires that subtasks are genuinely completed, preventing "spurious parallelism" — a form of reward hacking that just spawns subagents to inflate the parallelism metric. $\lambda_1,\lambda_2$ are annealed to 0 during training, ensuring the final objective optimizes only the true target. To measure the time cost under parallelism, the report defines **critical steps**: the wall-clock of a stage is determined by the longest-running subagent in that parallel group, and the whole episode's critical steps are the sum of the main agent's steps per stage plus that stage's longest subagent's steps. Using critical steps rather than total steps as the resource constraint forces the model to shorten the "longest parallel branch" instead of wildly spawning useless parallelism.

Notably, the degree of parallelism is not manually specified but "grows out" of the RL from environment feedback. Figure 4's two training curves support this: the left chart shows training accuracy rising smoothly from about 35% to about 65% over training steps, and the right chart shows average parallelism (the average number of subagents instantiated per episode) first dipping from about 8.5 to around 7.5, then climbing all the way to about 14. In other words, the orchestrator "first learns to get things right, then learns to parallelize only when it's worth it," rather than blindly splitting from the start.

### A concrete worked example: the three-setting ladder on BrowseComp

Reading the BrowseComp row all the way through best reveals the additive effect of each mechanism. A single K2.5 without context management gets 60.6%; switching on DeepSeek's Discard-all context management (truncating all history once a token threshold is exceeded) raises it to 74.9%; switching to Agent Swarm then reaches 78.4%, 17.8 percentage points higher than the single agent, even surpassing GPT-5.2 Pro's 77.9%. Agent Swarm wins because it breaks a long task into semantically isolated, individually bounded subtasks, with each subagent maintaining its own independent working memory and returning only "task-relevant output" — rather than the full interaction trajectory — to the orchestrator; this amounts to replacing "context truncation" with "context sharding," preserving information locality while adding an architectural dimension. Appendix E.8 discloses that under this setting BrowseComp caps the orchestrator at 15 steps and each subagent at 100 steps.

Evidence on the latency side is in Figure 8: on WideSearch, as the target Item-F1 rises from 30% to 70%, the single agent's execution time climbs from about 1.8× all the way past 7.0×, while Agent Swarm stays at a near-constant low latency of 0.6×–1.6×, corresponding to a 3×–4.5× speedup. This figure is the most direct visual evidence for the selling point that "parallelism turns task complexity from a linear expansion into parallel processing."

![Figure 8: On WideSearch, the horizontal axis is the target Item-F1 (30%→70%) and the vertical axis is the execution time (relative factor) needed to reach that target. Red dots are the single agent, blue dots are Agent Swarm; as the target rises, the single agent's execution time climbs past 7.0×, while Agent Swarm stays nearly flat around 1×, with the chart annotating speedups of save ×3.0 / ×3.2 / ×3.7 / ×4.5.](imgs/fig8_latency.png)

### Evaluation protocol and harness: the sampling settings you must know before reading Table 4

Table 4 merges six major categories and five opponents into one table, but the sampling protocols of the rows actually differ a lot, so you must lay out Appendix E's settings before reading. K2.5's general setting is temperature 1.0, top-p 0.95, context 256k; items that are public but have no ready-made scores are "re-tested by the authors under identical conditions and starred." By domain:

- **Reasoning** (HLE-Full, AIME 2025, HMMT, GPQA-Diamond, IMO-AnswerBench) uses a 96k-token completion cap; to reduce sampling variance, AIME 2025 and HMMT 2025 average over 64 independent runs (Avg@64), and GPQA-Diamond over 8 (Avg@8).
- **Code** all averages over 5 independent runs (Avg@5); the SWE-Bench series uses an "internally developed evaluation framework" (a minimal tool set of bash/create_file/insert/view/str_replace/submit), while Terminal Bench 2.0 is evaluated in non-thinking mode because the authors' thinking-mode context management is incompatible with Terminus-2's conversation state — both points discount comparability with other models.
- **Image/video** uniformly uses max 64k tokens and averages over 3 runs (Avg@3); video is further split: short clips (VideoMMMU, MMVU, MotionBench) sample 128 frames at a spatial-resolution cap of 896, and long clips (Video-MME, LongVideoBench, LVBench) sample 2048 frames at resolution 448.
- **Agentic search** by default does "no context management, counting anything exceeding the context window directly as a failure (no truncation)"; only Seal-0 and WideSearch use Avg@4, the rest single-run.
- **Computer-use** (OSWorld-Verified, WebArena) uses one-shot uniformly to save resources, with a per-turn cap of 100 steps, and for fairness only lets Claude Opus 4.5 use computer-use tools while deliberately excluding its browser tools (deviating from its System Card setting) — this practice of altering an opponent's tool set for the sake of alignment is itself a variable that may affect the opponent's score.

In one sentence: this table is not a set of level-headed numbers "run under one harness," but rather each domain's own protocol; before directly comparing magnitudes across rows, you must first confirm whether the number of samples and the tool settings are consistent.

## 🧪 Critical Assessment

### Is the problem real and important

Both core problems hold up. Multimodal's "fusion strategy under a fixed budget" is a real resource-allocation problem, and the linear latency of long-horizon agents is indeed a productization bottleneck — the report using its own Kimi K2-Thinking model as a counterexample (able to reason over hundreds of steps but with inference time growing linearly) is concrete and honest. Agent Swarm writing "latency" directly into the reward via critical steps is an elegant design that turns an engineering pain point into an optimizable objective; here the problem awareness and the method align well.

### Are baselines and evaluation settings comparable

This is where the whole report deserves the biggest discount. The authors themselves state that, because they "could not stably access the GPT-5.2 API," they skipped some high-cost benchmarks (such as WideSearch), and say that GPT-5.2 has about a 10% no-output failure rate on visual evaluations, all counted as wrong — this systematically depresses the opponent's score, and the authors also admit their own scores are therefore conservative lower bounds, which is a backward admission that the opponent's scores are underestimated. Many baseline numbers in Table 4 are starred (the authors' "internal re-tests" rather than officially published values) and are mixed into the same table as K2.5's own scores, so comparability is questionable. The BrowseComp comparison must be read carefully: the report body directly pits "K2.5's 74.9 with Discard-all context management on" against GPT-5.2's 65.8, Claude's 37.0, and Gemini's 37.8 — but all three of these opponent numbers are taken from the "context management off" row, which is a misaligned-setting presentation. Among these, 65.8 is GPT-5.2's only BrowseComp score in the entire Table 4 (the two rows in that column are merged into the same cell in the table, and the authors do not separately give GPT-5.2's "context-management-on" number). If the settings are aligned and both look at "context management off," K2.5 itself is actually 60.6, in fact lower than GPT-5.2's 65.8; K2.5 only pulls the score up to 74.9 to lead by relying on context management. Within the same table, the ones that genuinely have a separate "context-management-on" row are Claude (37.0→57.8), Gemini (37.8→59.2), and DeepSeek (51.4→67.6), and even after turning it on they still trail 74.9. The truly cross-level mismatch is the agentic item: Agent Swarm's 78.4 pits its own "multi-agent orchestration system" against GPT-5.2 Pro's "single model" 77.9 — fundamentally a comparison of different-tier systems.

### Self-built benchmarks and a curated front page

Of Agent Swarm's three evaluations, one is a fully self-built, externally non-reproducible "In-house Swarm Bench," on which K2.5 leads by 16.7 percentage points — achieving its largest lead on a custom, unreleased environment is the least persuasive. WorldVQA is also a benchmark released by Moonshot itself. Although the summary page's Figure 1 is not "a win in every cell" (as noted above, K2.5 is not first in five of the ten cells), which ten panels were chosen and why these particular items is not explained in the report, and combined with the visual arrangement of blue bars on the left, the overall presentation still leans toward "highlighting strengths and downplaying gaps." In the computer-use section, GPT-5.2's (8.6) and Gemini 3 Pro's (20.7) OSWorld scores are abnormally low and both come from internal re-tests; such extreme low scores, if not confirmed by the opponent side, are very likely harness incompatibility rather than a real capability gap.

### Is "visual agentic" an end-to-end proof or an assembly of per-item results

The report's signature is "visual agentic intelligence," but one must ask: is there a piece of quantitative evidence proving that "see the image → take action → get the answer" runs end-to-end? The answer is — quantitatively, no. Table 4's visual scores (MMMU-Pro, OCRBench, Video-MME…) are pure perception/understanding benchmarks, and the agentic scores (BrowseComp, OSWorld…) are mostly text or GUI scenarios; the two are listed separately, sampled separately, and there is no "perception-driven action" quantitative benchmark stringing the two ends together. What actually shows the complete perception→tool/code→answer loop is two **qualitative** example figures: Figure 12 shows K2.5 decomposing visual problems into executable programs (solving a maze with BFS graph traversal, computing pie-chart areas via pixel-level color segmentation, finding differences via CV pixel-difference comparison), and Figure 11 shows Agent Swarm using a hierarchical multi-agent setup to analyze a 24-hour, 40GB *Black Myth: Wukong* gameplay video and compile it into an HTML report. These examples read persuasively, but they are cherry-picked individual showcases, not reproducible statistical evidence; that is, "visual agentic" is currently a combination of the two separate capabilities "strong visual perception + strong agentic orchestration," with the end-to-end closed loop only qualitatively supported and still lacking quantitative benchmark backing.

### Novelty or engineering repackaging

Most components are integrations of existing ideas rather than brand-new algorithms: MoonViT/NaViT packing comes from Kimi-VL and prior work, MuonClip/QK-Clip come from Kimi K2, and Discard-all context management is directly cited from DeepSeek. What is genuinely newer is the empirical claim of "early low-ratio fusion," zero-vision SFT, and handing the parallelization decision to RL (PARL + critical steps). But "early fusion is better" rests only on Table 1's three settings, with tiny column gaps and no variance — the strength of evidence cannot support such a strong generalization; and zero-vision SFT's "adding manual visual trajectories is actually worse" is dispatched with a single line of "preliminary experiments" and no numbers. These are valuable observations, but closer to anecdotal engineering recipes than rigorously established principles.

### Gaps in safety, contamination control, and reproducibility

Compared with same-tier frontier model reports, this report lacks three key pieces of content: **no safety/risk evaluation section, no explanation of data contamination (contamination/decontamination) control, and no limitations section**. For a model that markets computer-use and autonomous agents (able to spawn subagents, run shell/IPython, download files), lacking a safety evaluation is especially serious. ## One-Minute Version

- **Early vision fusion**: K2.5 argues that under a fixed token budget, adding vision data at a low ratio (10:90) right at the start of training beats injecting a large amount later. Example: in a same-budget comparison, early injection is highest in five of six evaluations, with vision knowledge 25.8 beating late injection's 24.2.
- **Visual RL feeds back into text**: doing RL only on tasks that "require looking at the image to answer correctly" incidentally improves text-only capabilities as well. Example: after visual RL, text-only MMLU-Pro rises from 84.7 to 86.4 and GPQA-Diamond from 84.3 to 86.4.
- **Agent Swarm parallel speedup**: splitting a long task among multiple subagents working simultaneously solves the problem of latency exploding with step count when a single model does a long task. Example: on WideSearch, to reach the 70% target the single agent's execution time climbs past 7.0×, while Agent Swarm stays at a near-constant low latency of 0.6×–1.6×.
- **Evaluation comparisons are often not comparable**: many leads actually mix in biases from inconsistent settings on both sides, and you must return to the full table to correct for them. Example: on agentic, K2.5's 78.4 is the score of its "own multi-agent orchestration system," yet it is compared against GPT-5.2 Pro's "single model" 77.9 — a comparison of different-tier systems.
- **Safety and risk left blank**: the model can operate a computer, spawn subagents, run shell/IPython, and download files, yet the report has no safety/risk evaluation section at all and lacks any explanation of data contamination control and a limitations section — this is the piece you most need to supply yourself when reading this report.
